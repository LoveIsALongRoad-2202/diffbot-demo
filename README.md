# DiffBot — ROS2 + Gazebo Simulation with Real Arduino/L298N Bridge

A keyboard-controlled 4-wheel differential-drive car, simulated in Gazebo
and (once wired) drivable on real Arduino Uno + L298N + 18650 hardware,
using the **same `/cmd_vel` command stream** for both.

```
diffbot_ws/
├── src/diffbot_sim/          # ROS2 package: URDF, launch files, world, RViz config
├── arduino/diffbot_l298n/    # Arduino sketch for the real car
├── serial_bridge/            # PC-side node bridging ROS2 <-> Arduino serial
└── README.md                 # this file
```

---

## 1. Prerequisites (Ubuntu 22.04 + ROS2 Humble)

```bash
# ROS2 Humble (skip if already installed)
sudo apt update
sudo apt install ros-humble-desktop

# Gazebo + ROS2 integration + teleop + xacro
sudo apt install ros-humble-gazebo-ros-pkgs ros-humble-gazebo-ros \
    ros-humble-xacro ros-humble-robot-state-publisher \
    ros-humble-joint-state-publisher ros-humble-joint-state-publisher-gui \
    ros-humble-teleop-twist-keyboard ros-humble-rviz2 xterm

# Python serial library (for the serial_bridge_node, needed later for hardware)
pip install pyserial --break-system-packages
```

Source ROS2 in every new terminal (or add to `~/.bashrc`):
```bash
source /opt/ros/humble/setup.bash
```

cd ~/diffbot_ws

## 3. Run the Gazebo simulation (no hardware needed — do this NOW)

**Terminal 1** — launch Gazebo with the robot spawned:
```bash
source /opt/ros/humble/setup.bash
source ~/diffbot_ws/install/setup.bash
ros2 launch diffbot_sim gazebo_sim.launch.py
```
Gazebo should open showing a small 4-wheeled car on a ground plane with
two colored boxes as landmarks. RViz2 will also open showing TF frames.

**Terminal 2** — launch keyboard teleop:
```bash
source /opt/ros/humble/setup.bash
source ~/diffbot_ws/install/setup.bash
ros2 launch diffbot_sim teleop.launch.py
```
This opens an xterm window. Click into it and use:
```
   u    i    o
   j    k    l
   m    ,    .
```
`i`/`,` = forward/backward, `j`/`l` = turn left/right, `k` = stop.
Press `q`/`z` to change speed step.

You should see the robot move in Gazebo in real time — this is your full
360° drivable simulation, working right now with zero hardware.

**Verify feedback is live:**
```bash
ros2 topic echo /odom
```
You'll see position (x, y) and orientation (quaternion) updating as you drive —
that's the simulated "feedback" loop, generated by Gazebo's physics engine
from the wheel joint velocities, published in real time.

## 4. Arduino firmware (flash this once wiring is complete)

Open `arduino/diffbot_l298n/diffbot_l298n.ino` in the Arduino IDE.

**Wiring (edit pin numbers in the sketch if yours differ):**

| L298N Pin | Arduino Pin | Purpose              |
|-----------|-------------|-----------------------|
| ENA       | D5 (PWM)    | Left side speed       |
| IN1       | D7          | Left side direction A |
| IN2       | D8          | Left side direction B |
| ENB       | D6 (PWM)    | Right side speed      |
| IN3       | D9          | Right side direction A|
| IN4       | D10         | Right side direction B|
| GND       | GND         | **Common ground — critical** |
| 12V/VIN   | Battery pack +  | From 2x 18650 in series |
| GND       | Battery pack -  | From 2x 18650 in series |

Since you have 4 motors, wire the two LEFT motors to Channel A (both to
the same ENA/IN1/IN2, or paralleled at the motor driver output — check
your L298N board's current rating, ~2A per channel typically; 2 small
hobby motors in parallel per channel is usually fine but measure stall
current if unsure), and the two RIGHT motors to Channel B likewise.

**Important power note:** Do NOT power the Arduino's 5V pin from the
L298N's onboard 5V regulator while ALSO powering Arduino via USB during
testing — pick one 5V source at a time to avoid back-feeding. For bench
testing over USB (serial + power from PC), leave the L298N 5V-EN jumper
in place but don't connect L298N 5V output to Arduino 5V pin.

Upload the sketch with the Arduino connected via USB. Open Serial Monitor
at 115200 baud — you should NOT need to type anything; when idle it just
sits waiting for commands. Test manually by typing `L:150,R:150` and
pressing enter — wheels should spin forward. Type `L:0,R:0` to stop.

## 5. Bridge ROS2 to the real Arduino (once hardware + firmware are ready)

Find your Arduino's serial port:
```bash
ls /dev/ttyACM* /dev/ttyUSB*
# usually /dev/ttyACM0 on Ubuntu for Arduino Uno
```

Give yourself permission (once, then log out/in):
```bash
sudo usermod -a -G dialout $USER
```

Run the bridge node (Terminal 3, Arduino plugged in, Gazebo can stay
running too — same `/cmd_vel` drives both simultaneously):
```bash
source /opt/ros/humble/setup.bash
source ~/diffbot_ws/install/setup.bash
python3 ~/diffbot_ws/serial_bridge/serial_bridge_node.py --ros-args \
    -p serial_port:=/dev/ttyACM0 \
    -p wheel_separation:=0.18 \
    -p wheel_radius:=0.033 \
    -p max_linear_speed:=0.3
```

Now the SAME keyboard teleop from Terminal 2 drives the real car too.

**Calibrate `max_linear_speed`:** this is "how fast does the real car go
in m/s at full PWM (255)". Measure it: command full speed forward for a
timed 2 seconds, measure distance traveled with a tape measure, compute
`distance / 2.0` = your real max_linear_speed. Update the parameter.
Without this calibration, the dead-reckoning odometry estimate and the
PWM-to-velocity mapping will both be inaccurate (though the car will
still drive/turn correctly in direction, just not at a precisely known
speed).

**About feedback without encoders:** `/odom_estimate` published by this
node is a dead-reckoning estimate (integrates commanded velocity over
time) — NOT measured from real sensors. It will drift over time,
especially on turns and if wheels slip. This is expected and normal for
an open-loop rig. To view it:
```bash
ros2 topic echo /odom_estimate
```

## 6. Adding real encoder feedback later (optional upgrade path)

If you later add 2 wheel encoders (e.g. IR slot sensors on one left +
one right wheel), the firmware comment block in `diffbot_l298n.ino`
explains exactly how to extend the `OK:` message to include pulse
counts, and `serial_bridge_node.py`'s dead-reckoning integrator can be
swapped for true encoder-based odometry (much more accurate, no drift
correction needed for straight-line motion).

## 7. Architecture summary

```
Keyboard --> teleop_twist_keyboard --> /cmd_vel (Twist)
                                          |
                    ---------------------+---------------------
                    |                                         |
                    v                                         v
         Gazebo diff_drive plugin                  serial_bridge_node.py
         (simulated wheels + physics)               (real Arduino via USB)
                    |                                         |
                    v                                         v
              /odom (ground truth,             /odom_estimate (dead-reckoning,
              from sim physics)                 no encoders, will drift)
                    |                                         |
                    v                                         v
                  RViz2  <--------------------------------- RViz2
           (both can be visualized together for comparison)
```

Same brain (`/cmd_vel`), two bodies (simulated + real), so your Gazebo
demo today is a preview of exactly how the real robot will behave once
wiring is finished.
